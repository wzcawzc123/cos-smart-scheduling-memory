# M2 焦点补盲 — 双扳机 Collector 与 systemui 盲区消除（v0.2.0）

> UnifiedRootOptimizer M2 · 2026-10-07 · 实现 + 四场景实测全过
> 消除对象：M1 影子对账 v2 §2-A 的 30 条 missed（systemui 盲区链，占 missed 总量 77%）

## 1. 问题回顾

`inotify /dev/cpuset/top-app/cgroup.procs` 是前台检测的最佳实践，但有原理性盲区：**systemui 常驻 top-app cgroup**，下拉通知栏/锁屏期间 cgroup 成员无任何变化 → inotify 永不触发。影响是链式的——不但吞掉 `systemui` 自身那条（22），还吞掉"收起后回到原 App"的恢复事件（8），因为整个过程 cgroup 从未动过。

## 2. 方案：第二扳机 `focus_driver`

| 项 | 决定 | 依据 |
|----|------|------|
| 信号源 | `dumpsys window` 取 `mCurrentFocus` | 焦点窗口与 systemui 状态强相关；独立于 cgroup |
| 巡检间隔 | **1s**（`DriverPaths::focusPollMs`） | 单次实测 **14–20ms**（对比 `dumpsys activity` 300–1000ms），2% 单核占空可进常驻 |
| 去重 | **`FgShared` 共享前台状态**，`publish()` 原子判重 | 与 inotify 扳机共享 last-known，谁先到谁发，天然防双发 |
| 语义 | 只在**包名**变化时发事件 | 同包内 Activity 切换（微信内跳页）不算前台变化，与 inotify 语义一致 |
| 模式 | SHADOW 只读 | 不写任何系统节点 |

### 焦点值 → 包名提取规则（`pkg_from_focus`）

实测焦点取值分布（run4 真值 B 的 194 条，45 种不同值）逼出的规则：

| 焦点值形态 | 处理 | 理由 |
|-----------|------|------|
| `Window{hash u0 com.pkg/com.act}` | 取 `/` 前包名 | 常态（42/45 种） |
| `io.github.mangi.eta`（无斜杠） | 原样 | 单任务态 |
| `NotificationShade` / `StatusBar` / `NavigationBar` / `Keyguard` | → `com.android.systemui` | 无点窗口名，归一为真值同款包名 |
| `mCurrentFocus=null` | **忽略，保持 last** | 锁屏过渡态，无包名可报 |
| `Pop-Up Window` / `弹出式窗口` / `PopupWindow:xxx` / `ActionsDialog` | **忽略，保持 last** | 系统弹窗只给窗口标题，强行解析必错；且 ResumedActivity 语义下弹窗不改前台 |

原则：**宁可漏一个周期，不发错误包名**——漏的下一周期自愈，错的会污染状态机。

## 3. 实现

- `include/drivers.hpp`：新增 `FgShared`（mutex + `publish()/get()`）、`focusPollMs`，`fg_driver` 签名加 `FgSharedPtr`
- `src/drivers.cpp`：新增 `read_focus_raw()`（popen grep -m1）、`pkg_from_focus()`、`focus_driver()`；`fg_driver` 改走共享去重
- `src/main.cpp`：起第 5 线程 t5，版本 **v0.1.0 → v0.2.0**（功能迭代）
- 构建：NDK r26d + qemu binfmt（同会话 mount+register+build），`BUILD_RC=0` 零错误，产物 486,800 B，md5 `42f57c283e60d4c74b9924414482fa9a`

## 4. 验收（四场景全过）

### A. 盲区复现（下拉通知栏 → 收起 ×3，M1 的 30 条 missed 触发条件）

```
19:21:49 fg-focus com.android.systemui    ← 真值 19:21:47.995
19:21:52 fg-focus ai.x.grok               ← 收起后恢复
19:21:56 fg-focus com.android.systemui
19:22:00 fg-focus ai.x.grok
19:22:05 fg-focus com.android.systemui
19:22:08 fg-focus ai.x.grok
```
**对账（win 5s）：匹配 12/12 = 100%，包名 12/12 = 100%，missed = 0，spurious 1（fg-boot 初态）**

| 指标 | M1（无补盲） | M2（双扳机） |
|------|------|------|
| 盲区场景 missed | 30 条（A1 22 + A2 8） | **0** |
| 包名一致率 | 94% | **100%** |

### B. 常规切换（mm/QQ/Brave 进出 ×3）
两扳机协同、**每步恰好 1 条，零双发**：进入走 `fg-inotify`，回桌面走 `fg-focus`（focus 1s 内返回，比 inotify 的 cgroup+300ms+dumpsys 更快）。

### C. 同包 Activity 切换（微信内跳 朋友圈/搜索/聊天 三页）
**零事件**——包名去重生效，未污染事件流。回桌面才发 1 条。

### D. bootstrap
`fg-boot data=ai.x.grok`（真实 ResumedActivity，无 `(unknown)`），focus 首读与 bootstrap 判重成功、未双发。

## 5. 成本实测（60s 采样）

| 项 | 值 |
|----|----|
| uro 自身 CPU（utime+stime 增量） | 230ms / 60s = **0.38% 单核** |
| dumpsys window 子进程（按 20ms/s 估） | ~2% 单核 |
| **合计常驻** | **≈2.4% 单核** |
| 线程数 | 6（主 + 5 驱动），与启动时一致，无泄漏 |

对照：COSMemory 引擎的 `dumpsys activity lru` 每 3–10s 一次、单次 300–1000ms ≈ 10–30% 单核占空。焦点巡检便宜一个数量级。

## 6. 观察与遗留

1. **真值 A 在恢复事件上慢于我方**：`cmd statusbar collapse` 后 UserAwareMgr 平均延迟 ~4.5s 才报恢复，我方 focus ≤1s 即报 → 对账出现负时延（avg −0.92s，最 −3.63s）。这是我方更快，不是我方错；但也说明 **handleTopAppChanged 不是无延迟的地面真值**，后续对账应把"恢复类事件"的时延容差放宽或改用 focus 真值交叉。
2. focus 巡检尚未覆盖**锁屏**场景（`Keyguard` 映射已写但未实测），下次锁屏可顺手验证。
3. 1s 是可调参数；若日后要在待机场景进一步压成本，可做成"亮屏 1s / 灭屏 5s"的自适应（依赖 ScreenChanged，M4 观测体系接入后再说）。
