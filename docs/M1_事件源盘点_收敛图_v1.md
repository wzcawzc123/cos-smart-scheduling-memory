# M1 事件源盘点与收敛图 — COSMemory × CoreTurboScheduler

> UnifiedRootOptimizer M1 首个交付物 · v1.0 · 2026-10-07
> 依据：COSMemory 源码（/workspace/COSMemory @ v1.1.5+）、CoreTurboScheduler 源码（fork @ 107 commits）、设备实测
> M1 退出条件（v1.1 §9）：行为等价 + 重复 watcher 收敛——本文是等价性验收的基准账本

## 1. 现状盘点：两套系统各自采集什么

### 1.1 COSMemory（shell 引擎，2 条系统级循环 + 按需工具）

| 组件 | 机制 | 节奏 | 采集内容 |
|------|------|------|----------|
| service.sh watchdog | 轮询 | 30s | `pgrep memory.sh` 拉活 |
| **engine/memory.sh 主循环** | 轮询 | **full 轮 60s 一次（sleep 8），非 full sleep 2** | 每轮：`dumpsys activity lru` 快照 → lru 解析 → 死亡检测 → keepalive/reclaim 计划 → **PSI(/proc/pressure/memory avg10) + MemAvailable** → apply → freeze_reap |
| memtop.sh / snapshot.sh | 按需 | 面板触发 | dumpsys meminfo / lru（不进轮询） |

**重点**：主循环里 `dumpsys activity lru` 每 **3~10 秒**执行一次（sleep 2 快轮）。dumpsys 单次 0.3~1s CPU——**它是常驻负载的嫌疑贡献者之一**（与待机报告中"唤醒窗口 busy 84%"时间吻合，确认需 A/B：暂停引擎对照）。

### 1.2 CoreTurboScheduler（C++ 守护，9 条线程）

| 线程 | 机制 | 节奏 | 采集内容 |
|------|------|------|----------|
| configTriggerTask | 轮询 | 5s | mode.txt 情景模式 |
| jsonTriggerTask | **inotify** | 事件驱动 | config.json 热重载 |
| **cpuSetTriggerTask** | **inotify**(top-app/cgroup.procs)+500ms 防抖 | 事件驱动 | **前台 App**（全系统最佳实践） |
| sceneTickTask | 轮询 | 500ms | 场景 tick |
| screenStateTask | 轮询 | 可配 interval | 屏幕状态 |
| loadSamplingTask | 轮询 | 5s 起 | /proc/stat CPU 负载 |
| touchDetectTask | 轮询 | 待机 1s / 活跃 200ms | 触摸状态 |
| appProfileTask | 轮询 | 3~8s | 分 App 画像匹配 |
| gpuGuard | 轮询 | 3s | GPU 频率写后守护（v4.1 修复：变化才写） |

### 1.3 按需/外围

- 我们的探测工具（game_fp/baseline 采样器）——一次性归档，不属于常驻
- 游戏助手/GameSpace、Oplus 系统调度——**外部写入方**，作为约束源登记（见裁决报告）

## 2. 重叠矩阵（收敛的靶子）

| 信息 | COSMemory 现状 | CoreTurbo 现状 | 系统可用的更优源 | 收敛决策 |
|------|----------------|----------------|------------------|----------|
| **前台 App** | 无显式（lru 隐含） | inotify top-app ✓ | inotify（已是最优）+ logcat handleTopAppChanged 备胎 | **Event Collector 统一 inotify**，全系统唯一 |
| **进程快照(lru)** | 每 3~10s 自拉 dumpsys | 自拉（appProfile 内） | 单一采样点分发 | **最大节省点**：快照由 Collector 按需生成+缓存，订阅者共享 |
| **屏幕状态** | 无 | 轮询 | **系统广播 SCREEN_ON/OFF/USER_PRESENT（零轮询）** | Collector 订阅广播 |
| **配置变更** | 名单文件每轮读 | json=inotify ✓ / mode.txt=5s 轮询 ✗ | inotify 全覆盖 | mode.txt 改 inotify（补齐 CT 自己的短板） |
| **内存压力** | PSI+MemAvailable 每轮读 | 无 | 阈值触发才发事件 | Collector 阈值采样→发布 MemoryPressureChanged |
| **CPU 负载** | 无 | 5s 轮询 | 同左（合理） | 归 Collector，5s→订阅者共享 |
| **屏幕/触摸/场景 tick** | 无 | 500ms/200ms/1s 三线程 | 触摸可用 IN_TOUCH 事件(inotify /dev/input)降本 | M1 先镜像节奏，M3 再优化 |
| **watchdog 拉活** | 30s pgrep | 进程内 | 统一 Runtime 监督 | M1 后归一 |

**结论：两套系统共 11 条常驻循环/线程，采集 6 类互相重叠的信息；收敛后目标 = 1 个 Event Collector + 4 个驱动源（inotify×2、广播×1、阈值采样×1）。**

## 3. 目标 Event Collector 设计（M1 落地物）

### 3.1 事件 × 源映射（对应 v1.1 §4.1 EventBus）

| EventType | 源机制 | 触发 | 防抖 |
|-----------|--------|------|------|
| ForegroundChanged | inotify `/dev/cpuset/top-app/cgroup.procs` | 文件变化 | 500ms（沿用 CT 实证参数） |
| ScreenChanged | 广播 SCREEN_ON/OFF/USER_PRESENT | 系统广播 | 天然去重 |
| ModeChanged | inotify mode.txt | IN_MOVED_TO | — |
| ConfigChanged | inotify 名单/配置目录 | 事件 | parse 失败回滚 last-known-good |
| MemoryPressureChanged | PSI+MemAvailable 阈值采样 | 越阈值才发 | cooldown（沿用 COSMemory 参数） |
| ThermalChanged | thermal zone0(pa) 轮询（T-OBS） | 跨档才发 | 滞回（v1.1 §5.4） |
| ChargerChanged | power_supply/status 轮询 | 状态翻转才发 | — |
| ProcessDeath | 快照差分（Collector 内部） | 上轮有本轮无 | 证据链（P0-07） |
| TouchChanged / ControllerFault | M1 占位（镜像 CT 节奏） | — | — |

### 3.2 行为等价验收法（M1 退出）

1. **影子对照**：新 Collector 与两套旧源并行运行 N 小时，逐事件比对（前台切换时刻差 ≤1s、模式变更 ≤1s、内存压力事件不漏发）
2. **负载对账**：对照组（现状）vs 影子组的 dumpsys 次数、线程数、CPU 占用——影子不得劣化
3. 不改动 COSMemory / CoreTurbo 的任何执行行为（M2 才做接线）

## 4. 本轮的重要副产品发现

1. **COSMemory 主循环的 dumpsys 频率（每 3~10s）**：待机唤醒窗口 busy 84% 的头号嫌疑——建议 M1 期间加一条 A/B（临时停引擎采一轮对照），无论结果如何都值得在 M2 把"共享快照"落地
2. **mode.txt 用 5s 轮询而 json 用 inotify**——上游自己的不一致，收敛时顺手修
3. 触摸线程 200ms 轮询是最贵的采集（活跃期），M1 先镜像，Phase D 评估 `/dev/input` inotify 化

## 5. M1 执行序（从本文接续）

1. Event Collector + StateManager + Runtime 骨架（单守护、单线程事件队列）
2. 四大驱动源接入（top-app inotify / 广播 / mode+config inotify / 阈值采样）
3. 影子对照跑通 → 等价验收
4. （M2 起）COSMemory/CoreTurbo 作为执行器接入，旧 watcher 退役
