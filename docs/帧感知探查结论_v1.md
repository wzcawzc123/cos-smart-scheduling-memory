# 帧感知信号源探查结论（v1，2026-10-16）

> 目的：为"帧感知调度"（设计文档 §11.3 P2、缺口清单 A1）选定可用信号源。
> 方法：设备只读探测（`dumpsys` / `tracefs` / `atrace` / `perfetto`），未改动系统。
> 结论：**数据源存在且有两条可用路径**；但解析链路需要设计。

## 1. 探测结果

| 信号源 | 结果 | 可用性 |
|---|---|---|
| `dumpsys SurfaceFlinger --latency` | 返回单值 `8333333`（刷新间隔 ns），**无帧时间戳数组** | ❌ 不可用（Android 13+ 行为变更） |
| `dumpsys SurfaceFlinger --latency <layer>` | 同上（仅间隔） | ❌ |
| `dumpsys SurfaceFlinger --timestats` | 无输出 | ❌ |
| **`dumpsys gfxinfo <pkg>`** | ✅ 完整：Total frames / Janky frames / 百分位 / Missed Vsync / Slow UI thread / Frame deadline missed | ✅ 可用（**游戏有效性待验**） |
| **`atrace -t N gfx`** | ✅ 抓到 **18.7 MB / 5s** 压缩轨迹 | ✅ 数据源存在 |
| **`perfetto`** | ✅ 存在（`/system/bin/perfetto`） | ✅ 官方现代工具 |
| `tracefs`（`/sys/kernel/tracing`） | ✅ 已挂载，可 enable events 并抓文本 trace | ✅ 底层可用 |

## 2. 顺带修正一处此前的误报

体检报告里"SystemUI jank 26.6%"**是短窗口（60s）差分造成的偏差**。
系统自身长期统计（`dumpsys gfxinfo com.android.systemui`）：

```
Total frames rendered: 9266
Janky frames: 326 (3.52%)          ← 新口径（我们读的是这个）
Janky frames (legacy): 948 (10.23%) ← 旧口径
50th/90th/95th/99th percentile: 5 / 10 / 14 / 32 ms
```

→ SystemUI 实际健康（3.52%），此前结论过重。**教训：短窗口差分会被单次极端窗口放大，报告时应同时给长期值。**

## 3. 三条落地路径（按成本排序）

### 路径 A：`gfxinfo` 增强（最低成本）
- 现状：已接（读 `Total frames rendered` / `Janky frames`），对普通 App 有效
- 待验：**游戏（Vulkan/EGL）是否统计**（王者近 24h 采样 0 次 → 很可能是无效的）
- 行动：需要用户在游戏中实测一次

### 路径 B：`atrace`/`perfetto` + 离线解析（中等成本）
- 数据源已验证（18.7MB/5s）
- 问题：轨迹是压缩二进制，**设备上无法解析**（无 traceconv/trace_processor）
- 方案：
  1. 设备短窗口抓取（1-2s）→ 落到 `/sdcard`
  2. 定期传给 Linux 环境解析（python-perfetto 或 traceconv）
  3. 提取 `Choreographer#doFrame` 时间戳 → 帧间隔/jank
- 缺点：有延迟（非实时），不适合"卡顿前升频"；适合**离线分析/调参**

### 路径 C：ftrace 文本 + 自定义标记（实时、推荐方向）
- `tracefs` 已挂载，可抓**文本** `trace` 文件（之前实测 3s 抓到 586 行 sched_switch）
- 思路：
  1. 设置 `debug.atrace.tags.enableflags`（让系统在 Choreographer/绘制时写 atrace 标记）
  2. enable 少量 ftrace 事件（`tracing_mark_write`）
  3. **实时读** `/sys/kernel/tracing/trace`（文本）→ 解析帧标记 → 帧间隔
- 优点：文本、轻量、可实时；缺点：需要验证标记是否出现

### 路径 D：LSPosed hook Choreographer（最可控、成本最高）
- 钩 `Choreographer.doFrame` / `FrameCallback`，直接拿每帧回调时间
- 优点：精确、实时、可拿到具体 App 的帧
- 缺点：需维护 LSPosed 模块 + 作用域（我们已有 COSGuard/显示增强模块的经验）

## 4. 建议

1. **先做路径 A 的验证**（用户玩一局，看 gfxinfo 对游戏是否有数）——成本 5 分钟，决定 A 是否可用
2. 若 A 无效 → 做**路径 C 的验证**（ftrace 文本 + atrace 标记）——成本 30 分钟
3. 若 C 也需要重活 → 评估**路径 D**（LSPosed hook），因为实时性是"卡顿前升频"的前提
4. 路径 B 作为**离线分析**的补充（调参期用），不做实时

## 5. 与同类项目对照

| 项目 | 帧感知做法 |
|---|---|
| Uperf（yc9559） | 注入 SurfaceFlinger（读渲染开始/滞后/结束信号） |
| NovaSched（ZenJooo） | NovaFAS：解析 SurfaceFlinger **timestats**（HyperOS 实测重写解析器） |
| fas-rs（shadow3aaa） | Frame aware scheduling（1.1k star，Rust） |

→ 三者都**直连 SurfaceFlinger 层**，说明 `gfxinfo` 那条路对游戏确实不够用。
我们的选项 C（ftrace 标记）本质上是"轻量版 SF 接入"，选项 D 是"hook 版"。
