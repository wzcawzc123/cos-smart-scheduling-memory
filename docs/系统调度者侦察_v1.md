# 系统调度者侦察 v1（2026-10-16）

> 目的：回答"能不能全部屏蔽系统调度，由 URO 全程接管"。
> 方法：设备只读侦察（fd 持有者扫描 + 配置文件 + Binder 服务 + 字符串分析）。
> 结论：**"全部屏蔽"不可行也不必要**；但发现了一个重要事实——**系统里已经有一个帧感知调度器（oiface）**，
> 它补上了我们缺的那块能力，正确的关系是**协作**而非对抗。

## 1. 谁在写频率？（fd 持有者扫描，全量）

扫描 `/proc/*/fd` 中指向频率节点的句柄，**全机只有两个进程**：

| 进程 | 命中数 | 持有节点 |
|---|---|---|
| **`oiface`**（pid 7529，`/system_ext/bin/oiface`） | **18** | CPU：policy0/3/7 的 `scaling_{cur,max,min}_freq`（全部三簇）<br>GPU：`gpuclk`、`gpu_load`、devfreq `max_freq`、`gpu_available_frequencies` |
| `system_server`（pid 3338） | 1 | （轻微） |

**→ 之前观察到的"系统每 6 秒改一次 max_freq"，写者就是这个 `oiface`。**

## 2. oiface 是什么

```
/system_ext/bin/oiface          880 KB · uid 1000 · PPid 1（init 启动）
进程名:  Binder:oiface
Binder:  oiface      → com.oppo.oiface.IOIfaceService
         oplusoiface → com.oplus.oiface.IOIfaceService
配置:    /system_ext/etc/oiface/oiface.config
启动:    /system_ext/etc/init/oiface.rc
```

### 它的能力（从字符串 + 配置还原）

| 能力 | 证据 |
|---|---|
| **帧率感知** | `BINDER_MESSAGE_FPS_CHANGE`、`getTotalFlipsFromSf`（从 SurfaceFlinger 取翻转数）、`getTotalFpsByLayerName`、`getFPS` |
| **卡顿救援** | `FrameRescuer getTargetFps`、**`"%dms no frame produced boost boost boost"`** |
| **调频执行** | 持有三簇 max/min_freq + GPU 时钟句柄；`getGpuFreqMaxSet`/`MinSet` |
| **per-game 配置** | `oifacegame` 段：每个游戏一个 `enable`，王者另有 `has_start_signal` + **SF layer 名** |
| **场景识别** | `oifaceim` 段：微信 `scene301/scene401` 带参数（[12,2000]） |
| **内核接口** | `/proc/oplus_frame_boost/{ctrl,sys_ctrl,stune_boost,info}`（内核模块，`ctrl` 权限 777） |

### 配置片段（`oiface.config`）

```json
"oifacegame": {
    "enable": 4294967295,
    "com.tencent.tmgp.sgame": {
        "has_start_signal": 1,
        "layer": "SurfaceView - com.tencent.tmgp.sgame/..."
    },
    "com.tencent.tmgp.cod": { "enable": 1 },
    ...
}
```

## 3. 系统调度体系全貌（分层）

```
Java 层   游戏助手 com.oplus.games ──→ COSA auto perf（可 hook，已定位）
              │
服务层    oiface（帧感知 + 调频）★ 唯一持有频率句柄者
          oplus_perf_service / performance_hint（Android 官方 ADPF）/ athena
              │
HAL 层    vendor.oplus.hardware.performance.IPerformance
          gameopt-service / perf-hal-2-3
              │
内核层    /proc/oplus_frame_boost/*（帧 boost 节点，可写）
          uag governor（实时调度）
```

## 4. 对"全部屏蔽"的结论

| 想屏蔽的 | 能不能 | 该不该 |
|---|---|---|
| 游戏助手调度 | ✅ 能（LSPosed，已定位 `setAutoPerfModeSwitchStatus`） | ✅ 该（与 URO 目标冲突） |
| **oiface** | 🟡 能（改配置 / 停服务） | ❌ **不该**——它做的正是我们缺的"帧感知" |
| HAL（perf-hal/gameopt） | ❌ 难（native） | ❌ 不该（相机/显示/充电都依赖） |
| 热控 / 电流保护 | ❌ 难 | 🔴 **红线，绝不能碰** |
| uag governor | ❌ 碰不到（内核态） | ❌ 不该（实时调度只能由它做） |

**"全部屏蔽"的致命问题**：屏蔽了之后，谁来做事？
- 没有 governor → 没有实时调度
- 没有 oiface → 没有帧感知（我们自己的还没做出来）
- 没有热控 → 硬件安全风险

## 5. 正确的关系：分工，而不是取代

```
URO           ：策略层——判档、定边界（频率上下限、参数）        ← 已接管
oiface        ：帧层——帧感知、卡顿即时响应、在边界内调频        ← 保留
uag governor  ：毫秒级——在边界内选频率                        ← 保留
thermal/BCL   ：安全——永远有效                               ← 保留
```

**这样做的理由**：
1. 我们和 oiface 的**时间尺度不同**（我们是秒/分钟级策略；它是帧级 ms 响应）——不冲突
2. 它已经实现了帧感知（我们最缺的能力）——**重复造轮子不划算**
3. 我们写边界会**限制**它的动作范围 → 实际上是"我们定规则，它执行"

## 6. 新机会（这次侦察最有价值的产出）

| 机会 | 说明 |
|---|---|
| **帧感知数据源** | oiface 有 `getTotalFpsByLayerName` / `getTotalFlipsFromSf` → 可作我们的帧率输入，**不必自己注入 SF** |
| **per-game 开关** | `oiface.config` 的 `oifacegame.<pkg>.enable` → 可按需（不）让它介入 |
| **内核 boost 节点** | `/proc/oplus_frame_boost/ctrl`（777 可写）→ 可调它的帧 boost 行为 |
| **边界协调** | 我们写 `scaling_max_freq`，它在其内调频 → 天然的分工接口 |

## 7. 建议的下一步

1. **试探 `IOIfaceService` 的帧率接口**（`service call oiface ...` 或写个 binder 客户端）
   → 若可用，**帧感知缺口直接补上**，不必做 LSPosed hook
2. **读 `/proc/oplus_frame_boost/info`**（只读）→ 看它的实时状态
3. 用另一台设备的思路验证不了，故**需在本机实测**（帧率接口 + 游戏场景）
4. 之后再决定游戏助手 hook 是否还有必要（如果 oiface 已覆盖帧感知，游戏助手的 auto perf 就更像是冗余了）
