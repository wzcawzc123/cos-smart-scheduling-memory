## 2. 各段核心指标

| 指标 | NORMAL | GAME | CHARGING |
|------|--------|------|----------|
| CPU busy avg / p90 | **71 / 89%** | 38 / 50% | 51 / 84% |

要点：
- **02:58–03:34 高强度日常段耗电 14%/36min ≈ 23%/h**（busy 71%、亮屏高刷）——这是本机"重度亮屏"的真实功耗水位
- **游戏+充电叠加时 pa 冲到 54.8°C**——即使温控被移除，真实传感器（zone0 pa 不在伪造名单）显示这是机器的物理热点
- 游戏段 PSI cpu 28.6 高于日常——120 帧游戏确实带来 CPU 压力，但 busy 仅 38% → **压力来自调度延迟而非纯算力**（对 M3 策略有参考价值）

## 3. 频率钳制分布（第三写入方的量化证据）

各段 `scaling_max_freq` 出现频次 Top3：

| 段 | P0(小核) max | P3(中核) max | P7(大核) max |
|----|---------------|---------------|---------------|
| NORMAL | 2016000:115 / 1459200:43 | 2803200:74 / 2323200:53 | **3187200:104**（约 61% 时间全速） |
| GAME | **1670400:156**（94% 时间被压 1.67G） | 2323200:47 / 1171200:31 / 1920000:18 | 2476800:43 / 1977600:32 / 1363200:23 |
| CHARGING | 1670400:155 / 2016000:109 | 2323200:121 | 2592000:75 / 3187200:43 |

解读：
1. **三种状态三个档位面**：日常大核可全速、游戏被压到 ~2.48GHz 以下、充电再压到 2.59GHz——系统按"场景+充电态"整面钳制，不是逐负载微调
2. 游戏段 P7 的三个主档（2476800 / 1977600 / 1363200）**与三次性能模式切换对应**——即使插电充电，电竞模式也只放开到 2476800，**未到硬件 3187200**（充电热限制叠加模式上限）
3. 游戏段 P0 有 94% 时间被钉在 1670400（HW 上限 2016000）——小核被系统性压频
4. **对 M3 的裁定**：`scaling_max` 是三方争用的"状态面"而非可快照的基线；Constraint Engine 的 `kernelSupportedMax` 必须取 `cpuinfo_max_freq`；我们写入后按 generation+低频 readback 重申，**绝不进入高频对写**

## 4. 电流单位标定（结论：**未通过，降级使用**）

| 方法 | 结果 |
|------|------|
| 充电段容量斜率法 | 31%→100% / 1.27h = **2712mA** 等效充电电流（50mAh/%，5000mAh 电池） |
| current_now 读数均值 | **-592** |
| 偏差 | **4.6 倍** |

**判定**：`current_now` 量纲既不是 µA 也不是可信的电池主回路 mA（可能为分路/HAL 缩放值，Extreme GT 的充电脚本也可能介入）。**降级处理**：绝对功耗计算禁用此读数；仅作符号（充/放）与相对趋势信号；真要功耗绝对值需换 `power_supply` 其它节点或 KEVENT 充电日志交叉标定（列下一轮）。
- 附带印证：logcat KEVENT `batt_curr` 与 current_now 同量纲同数量级 → 二者同源，一起存疑
