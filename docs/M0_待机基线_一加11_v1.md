# M0 待机基线报告 — 一加11 · 6 小时深度 Doze 实测

> UnifiedRootOptimizer 阶段 0 产出 · v1.0 · 2026-10-06
> 会话：11:49:26 – 17:54:50（**6.09h**），30s 间隔，守护 dm_73c21d7f
> 数据：`docs/evidence/standby_1006_1149.log`（起止归因快照 + 65 个唤醒帧）
> 条件：电量 99% 起、放电中、未充电、位置未动；**Extreme GT 在位**（shell 伪造值不参与）

## 0. 采样机制发现（方法论，先记）

熄屏深度挂起时 **AP 冻结、进程暂停**——`sleep` 不走、时间跳变，所以 6 小时只落 65 帧。这不是缺陷：**帧 ≈ 每次真实唤醒窗口**，帧数与间隔本身就是待机质量的直接度量（后文 wake-gap 即由此得出）。下版采样器按此设计：帧时间戳 + 挂起时长双轨记录。

## 5. 对 M0 与设计的裁定

1. **本轮可用性**：✅ 作为"**现状真实基线**"完全成立——它记录的正是设备在当前 App 生态下的真实待机（差），这比一份无污染的漂亮数字更有工程价值
2. **污染说明**：若需"干净待机"对照（排除微信/QQ），需另测一轮（退出双开+QQ 后锁屏）——列可选
3. **设计回写**：
   - `SCREEN_OFF` 场景的价值获得量化证据（唤醒 10/h、busy 84% → M3 的熄屏策略有巨大收益空间）
   - 与 COSMemory 直接联动：appbrand 常驻烧 CPU 正是 Freeze/后台治理的目标形态
   - 通知白名单 200+ 是结构性问题，属产品决策非调度能解——报告给用户自行取舍
4. **P1-03（空闲开销验收）参照系确定**：3.0%/h 即改造前水位，验收目标建议 ≤1.5%/h

## 6. 本轮方法论教训

1. AP 挂起冻结采样进程 → 帧=唤醒窗口，是特性不是 bug（§0）
2. `tr -d ' '` 压扁字段导致首轮状态解析失败 → 字段分隔符规范写入采样器契约
3. `daemon_stop` 工具参数注入 bug → 临时用 `kill -9 <pid>` 绕过（已记）
4. 起止 alarm 快照 diff 这套归因手法有效，下轮保留并扩展（加 batterystats kernel wakeup 源）
